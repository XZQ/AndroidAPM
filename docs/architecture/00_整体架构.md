# AndroidAPM 整体架构

> 同步日期：2026-07-21｜以当前源码、构建配置与测试为准

## 1. 系统边界

AndroidAPM 是端上 SDK，不是完整托管 APM 产品。

仓库内：

- 15 个 Android 监控模块
- 统一事件模型和上下文
- 分发、限流、可选聚合与默认启用的 PII 脱敏
- SQLite durable outbox、File 兼容存储
- 稳定 eventId、本地幂等与跨进程 claim/lease/expiry
- HTTP/Logcat/自定义 uploader
- 逐请求短期鉴权、签名远程配置、LKG、kill switch、动态采样/限流/HTTPS endpoint
- 可选多进程文件 hand-off
- SDK 自监控、独立本地诊断日志和自动降级
- 手动 Trace API、OTel-compatible Map
- ASM Gradle 插件和示例应用
- 非发布 AndroidX Microbenchmark harness

仓库外：

- 生产 Collector、鉴权、租户
- 数据查询、聚合、告警、Dashboard
- Native 符号化服务
- 服务端事件去重与幂等
- 外部 Maven 仓库

## 2. 构建拓扑

```text
26 build units
├─ 24 root subprojects
│  ├─ 5 foundation: model / core / storage / uploader / remote-config
│  ├─ 15 monitoring modules
│  ├─ 2 extensions: trace / otel-exporter
│  ├─ 1 sample app
│  └─ 1 non-published benchmark module
└─ 2 included builds
   ├─ apm-plugin
   └─ build-logic
```

所有构建单元统一使用 Java 17 toolchain，并允许 Gradle/AGP 支持的更新 JDK 作为 Gradle runtime；Android、纯 JVM、Gradle 插件和独立 consumer 的 Java/Kotlin 字节码目标均为 17。

所有监控模块通过 `api(project(":apm-core"))` 暴露统一接入入口，并通过 `apm-model` 构造事件。`apm-core` 依赖 storage，API 暴露 model/uploader。`apm-otel-exporter` 只依赖 model；`apm-plugin` 只参与编译期。

## 3. 运行时主链路

```text
Monitor / Trace
  │
  ├─ Apm.emit
  │    caller captures timestamp, threadName and payload snapshots
  │    bizContext: exact synchronous snapshot or O(1) async-cache read
  │
  ├─ ApmContext
  │    main/uploader process -> dispatcher
  │    child process + coordination -> IPC file hand-off
  │
  ├─ ApmDispatcher queue
  │    ArrayBlockingQueue capacity 2048
  │    admission uses tryLock + offer; producers never wait
  │    default high-water isolation: 75% queue / 50% per NORMAL/LOW module
  │    higher priority may atomically evict oldest lower priority
  │
  ├─ worker batch (first + drainTo, max 32)
  │    resolve lazy event
  │    -> signed dynamic sample (ERROR/FATAL bypass)
  │    -> optional aggregate
  │    -> dynamic rate limit (ERROR/FATAL bypass)
  │    -> default PII sanitize (text patterns + sensitive field names)
  │    -> EventStore.appendBatch
  │
  ├─ SQLiteEventStore
  │    schema v3 / WAL / 50,000 rows / 64 MiB live payload / unique eventId
  │    256 KiB per-event soft limit / priority eviction / claim lease
  │
  ├─ PersistentUploadWorker
  │    claimPending(owner, expiry) -> upload once
  │    success: owner-aware acknowledgeClaim
  │    failure: failClaim -> release -> prune when exhausted -> backoff
  │
  └─ HttpApmUploader / custom uploader
       batch POST / optional Protobuf / default Gzip
       per-request short-lived auth / optional signed HTTPS endpoint rotation
       2xx success / 429 or 503 Retry-After
```

## 4. 关键事件

`Apm.emitCriticalSync` 立即构建事件并到达本地 durable hand-off point：

- uploader process：同步 `store.append`，随后 signal worker
- 非 uploader process 且启用协调：同步发布单独 IPC 文件

该路径不等待网络。若使用 `StorageType.FILE`，只能同步写非 durable ring buffer，无法获得 restart replay/acknowledged delete 语义。

## 5. 交付语义

当前语义是 acknowledged at-least-once：

- 只有 uploader 返回完整批次成功才删除 outbox 行
- 失败保留并增加 retry count
- 本地指数退避与服务端 `Retry-After` 取较大值
- retry 失败达到 `maxRetries + 1` 或事件时间超过 7 天后清理
- 进程重启后 worker 从 SQLite 重放

不保证 exactly-once：

- `ApmEvent.eventId` 在 Line/Protobuf/codec/SQLite/IPC 全程稳定，供服务端幂等
- 服务端成功但客户端未收到响应时会重发
- SQLite 写事务原子 claim；owner-only ACK/failure；expiry 后可重领
- 网络不确定性仍要求服务端按 eventId 去重

## 6. 生命周期

```text
Apm.register before init
  -> module retained

Apm.init
  -> create independent diagnostics + logger
  -> create store/uploader/limiter/aggregator/sanitizer/self-monitor
  -> create business-context source; async mode starts apm-biz-context refresh
  -> create dispatcher
  -> optional ProcessEventCoordinator
  -> start managed signed-config polling
  -> start every registered module that passes process/dynamic/gray filters

Apm.register after init
  -> atomic duplicate-name check
  -> initialize and start immediately when filters allow

Apm.stop
  -> state=null, reject new emits
  -> stop signed-config polling
  -> stop business-context refresh
  -> stop self-monitor/coordinator
  -> module.onStop
  -> drain dispatcher with timeout
  -> flush aggregation residue
  -> stop worker/uploader
  -> close store
```

模块启动受进程策略、全局 `apm.enabled`、模块签名开关、`GrayReleaseController` 和当前 AutoThrottle 集合过滤。托管 provider 发布新可信快照后在 `initLock` 下动态停止或恢复模块；自动健康降级立即生效，连续 3 个健康周期后才释放，并在恢复时重新检查其余门禁。

## 7. 多进程

多进程协调默认关闭。开启时主进程为 uploader process：

```text
child process event
  -> buffer on apm-ipc-write
  -> flush at 100 lines or 500 ms
  -> write unique .tmp
  -> rename to .ipc
  -> main process scan every 5 s
  -> decode complete ApmEvent
  -> dispatcher
```

critical 事件绕过缓冲并同步发布。`.ipc` 文件 5 分钟过期；遗留 `.tmp` 也按超时清理。rename 失败会 copy 到 ready 文件后删除 temp，这一 fallback 不应被解释成跨文件系统事务保证。

## 8. 线程与执行器

| 线程/执行器 | 作用 | 优先级意图 |
|---|---|---|
| `apm-dispatcher` | 解析、聚合、限流、脱敏、批量落盘 | 后台管线；当前为命名 daemon Thread |
| `apm-persistent-upload` | outbox 顺序上传与重试 | background |
| `apm-aggregation` | 过期聚合窗口 flush | background |
| `apm-self-monitor` | SDK 健康报告/auto-throttle | background |
| `apm-biz-context` | 可选业务上下文异步刷新与 LKG 发布 | background；emit 不等待 provider |
| `apm-diagnostics-writer` | 独立诊断 JSONL 落盘 | background |
| `apm-ipc-write` / `scan` | IPC 合批发布/扫描 | background |
| 模块采样线程 | Memory/GC/Thread/Battery 等 | background 或 measurement |
| `apm-anr-*` | Watchdog/SIGQUIT 分析 | measurement |
| slow-method sampler | 主线程栈采样 | measurement |

`ApmExecutors` 统一 daemon、线程名和两级优先级。`apm-uploader` 无法依赖 core，因此保留模块内执行器和 `UploaderLogger`。

## 9. 资源保护

- dispatcher queue：2048
- dispatcher module isolation：默认开启；75% 高水位后单一 NORMAL/LOW 来源最多占总容量 50%，HIGH/CRITICAL 绕过
- dispatcher drain：32
- biz-context refresh：异步模式 100 ms–24 h 有界；显式刷新最多保留一个 pending 请求
- SQLite rows：50,000
- SQLite live payload：64 MiB 逻辑预算（不含 page/WAL；活动租约可使回收延后）
- SQLite durable event：256 KiB 软上限（codec 仍保留 2 MiB 硬上限）
- RateLimiter bucket LRU：256
- non-durable uploader queue：500
- aggregation bucket/sample：有硬上限
- stack fingerprint cache：有硬上限
- IPC file batch：100 行
- codec event payload：2 MiB 硬上限
- event map：4096 entries
- diagnostics memory/queue：200 / 256 records，且各自最多 4 MiB
- diagnostics files：3 × 512 KiB

发生过载时优先丢低价值事件并记录自监控，而不是让资源无界增长。

## 10. 配置默认行为

| 能力 | 默认 |
|---|---|
| SQLite durable outbox | 开 |
| HTTP Gzip | 开（只有 HTTP endpoint 时生效） |
| Dynamic HTTP endpoint | 关；开启后仍只接受无凭据 HTTPS URL |
| Static/dynamic HTTP headers | 空；动态 provider 每请求读取短期凭据 |
| Signed config polling | 仅配置 `SignedRemoteConfigProvider` 后启用；默认 15 分钟 |
| Self monitoring / auto-throttle | 开 |
| Aggregation | 关 |
| PII sanitization | 开；文本规则 + 高置信敏感字段名 |
| Debug logging | 关 |
| Multi-process coordination | 关 |
| Native crash | 关 |
| Hprof / fork dump | 关 |
| Endpoint | 空，安全丢弃且不输出 payload；Logcat 需显式 `logcat://...` |

“实现存在”不等于“默认开启”；生产配置必须显式评审隐私、采样、进程、网络和高风险 Native/Hprof 能力。

## 11. 监控层接入分类

自动/生命周期驱动：Crash、ANR、Memory 周期采样、Launch、FPS、Thread、GC、Render。

宿主接线：Network、SQLite、IPC 显式 trace、指定 WebView install/wrapper、注册 ThreadPoolExecutor、Battery 的 WakeLock/GPS/Alarm、IO stream wrapper、Launch 精细阶段。

编译期接线：Slow Method ASM 插件。

公共 API 无法可靠支持的通用 Binder hidden hook、进程级 WebView auto-register、通用 thread leak 和 GPU overdraw 字段已弃用并默认关闭。线程池 backlog、WebView delegate instrumentation 与 FrameMetrics 使用显式/受支持 API 实现。

## 12. 自监控与独立诊断

`SdkSelfMonitor` 记录 emit、drop、queue size、upload latency、internal errors、dispatcher 模块隔离丢弃、存储拒绝/容量淘汰、诊断队列丢弃和诊断文件失败。`dispatcherModuleIsolationDropCount` 是总 drop 的可归因子集。健康报告可驱动 `AutoThrottle`：高丢弃率或高延迟时立即停用低优先级模块；极高丢弃率再停用部分 normal 模块。恢复要求连续 3 个周期同时满足 drop rate <= 20% 和平均上传延迟 <= 3 秒；迟滞区间或新退化会清零恢复计数。

每个 `sdk_health` 先把仅含数值计数的摘要写入独立诊断 journal，再以 HIGH 优先级尝试普通事件管线；后者仍可能受采样、限流或极端拥塞影响，但前者不依赖 dispatcher/outbox/uploader。详细 SDK 错误同样写入独立的 Logcat + 内存环 + app-private 滚动 JSONL；journal 按 Android 进程隔离，聚合导出会合并所有进程。内存和写队列同时受条数/字节双预算约束，冷却期间先等待再出队，读写失败分开统计。`ApmDiagnostics` 提供同步兼容及 executor 异步读取/导出、当前进程清理和显式全进程清理；诊断包默认不自动上传。

## 13. 外部演进边界

客户端可独立完成的 eventId、schema v3、claim lease、动态短期鉴权、签名配置/LKG/kill switch/采样/限流/endpoint、优先级感知背压、默认隐私保护和运行时快照已完成。Collector 的 Token 签发/撤销、配置签名与 rollout、查询/告警、服务端幂等、typed-field 版本协商、真机性能预算、Native 符号化、外部 Maven 与云端 CI 的唯一清单由独立 `AndroidAPM-Server` 仓库的 `docs/云端待建设清单.md` 维护。
