# AndroidAPM 整体架构

> 同步日期：2026-08-23｜以当前源码、构建配置与测试为准

## 1. 系统边界

AndroidAPM 是端上 SDK，不是完整托管 APM 产品。

仓库内：

- 15 个 Android 监控模块
- 初始化前 fail-closed strict production profile、显式 consent 与撤回清理
- 统一事件模型和上下文
- typed durable codec v3，并兼容读取 v1/v2 字符串字段
- 显式 protobuf envelope V2：typed fields、standard resource、schema/SDK、batch ID、大小与 ACK
- 分发、限流、可选聚合与默认启用的 PII 脱敏
- SQLite durable outbox、File 兼容存储
- 稳定 eventId、本地幂等与跨进程 claim/lease/expiry
- HTTP/Logcat/自定义 uploader
- 逐请求短期鉴权、签名远程配置、LKG、kill switch、动态采样/限流/HTTPS endpoint
- 可选多进程文件 hand-off
- SDK 自监控、独立本地诊断日志和自动降级
- 手动 Trace API、OTel-compatible Map
- 单依赖完整客户端分发 Bundle
- ASM Gradle 插件和示例应用
- 非发布 AndroidX Microbenchmark、固定 time/allocation 预算与 fail-closed 物理设备 gate

仓库外：

- 生产 Collector、鉴权、租户
- 数据查询、聚合、告警、Dashboard
- Native 符号化服务
- 服务端事件去重与幂等
- 外部 Maven 仓库

## 2. 构建拓扑

```text
27 build units
├─ 25 root subprojects
│  ├─ 5 foundation: model / core / storage / uploader / remote-config
│  ├─ 15 monitoring modules
│  ├─ 2 extensions: trace / otel-exporter
│  ├─ 1 distribution: apm-bundle
│  ├─ 1 sample app
│  └─ 1 non-published benchmark module
└─ 2 included builds
   ├─ apm-plugin
   └─ build-logic
```

所有构建单元统一使用 Java 17 toolchain，并允许 Gradle/AGP 支持的更新 JDK 作为 Gradle runtime；Android、纯 JVM、Gradle 插件和独立 consumer 的 Java/Kotlin 字节码目标均为 17。

仓库根 `.java-version` 声明推荐 JDK 17；`settings.gradle.kts` 在任何项目配置前拒绝低于 17 的 Gradle runtime。平台无关的 `python tools/verify_ci.py` 先校验实际 Java，再验证 23 个根发布制品与 included `apm-plugin` 的已提交公开 ABI、四个独立 build root 的依赖 SHA-256 元数据和 25 坐标发布候选，检查基线范围/非空性，并以 `--rerun-tasks` 执行根 Android/model、included plugin 和文档门禁，使本地与托管 CI 复用同一入口。公开面和 SemVer 规则见 [API 兼容策略](../API_COMPATIBILITY.md)，制品、签名、SBOM 和外部仓库边界见 [发布与供应链门禁](../RELEASE_PROCESS.md)。

所有监控模块通过 `api(project(":apm-core"))` 暴露统一接入入口，并通过 `apm-model` 构造事件。`apm-core` 依赖 storage，API 暴露 model/uploader。`apm-otel-exporter` 只依赖 model；`apm-plugin` 只参与编译期。`apm-bundle` 是不承载实现类的分发层，通过 POM 传递暴露 22 个运行时模块，不改变运行时依赖方向，也不会自动应用构建期插件。

## 3. 运行时主链路

```text
Monitor / Trace
  │
  ├─ Apm.emit
  │    caller captures timestamp, threadName and payload snapshots
  │    bizContext: exact synchronous snapshot or O(1) async-cache read
  │
  ├─ ApmContext
  │    main/uploader process -> dispatcher
  │    child process + coordination -> IPC file hand-off
  │
  ├─ ApmDispatcher queue
  │    ArrayBlockingQueue capacity 2048 + 8 MiB estimated retained bytes
  │    admission uses tryLock + offer; producers never wait
  │    default high-water isolation: 75% queue / 50% per NORMAL/LOW module
  │    higher priority may atomically evict enough oldest lower-priority entries
  │
  ├─ worker batch (first + drainTo, max 32)
  │    resolve lazy event
  │    -> signed dynamic sample (ERROR/FATAL bypass)
  │    -> optional aggregate
  │    -> dynamic rate limit (ERROR/FATAL bypass)
  │    -> default PII sanitize (text patterns + sensitive field names)
  │    -> EventStore.appendBatch
  │
  ├─ SQLiteEventStore
  │    schema v4 (additive claim-order index) / WAL / 50,000 rows / 64 MiB live payload / unique eventId
  │    256 KiB per-event soft limit / priority eviction / claim lease
  │
  ├─ PersistentUploadWorker
  │    claimPending(owner, expiry) -> upload once
  │    success: owner-aware acknowledgeClaim
  │    failure: failClaim -> release -> prune when exhausted -> backoff
  │
  └─ HttpApmUploader / custom uploader
       batch POST / legacy or versioned Protobuf / default Gzip
       per-request short-lived auth / optional signed HTTPS endpoint rotation
       V2: encoded-byte split + exact whole-batch ACK; legacy: 2xx success
       429 or 503 Retry-After
```

strict built-in HTTP 使用 `PROTOBUF_ENVELOPE_V2`：gzip 前按 1 MiB 默认/4 MiB 绝对字节预算拆批，每个物理 batch 携带固定 resource 与 retry-stable batchId；2xx 还必须精确 ACK schema、batchId 和 event count 才允许 durable delete。legacy Line/standalone Protobuf 保持兼容，不被静默解释为 V2。

## 4. 关键事件

`Apm.emitCriticalSync` 立即构建事件并到达本地 durable hand-off point：

- uploader process：同步 `store.append`，随后 signal worker
- 非 uploader process 且启用协调：同步发布单独 IPC 文件
- 任意较低调用方 priority 自动提升为 CRITICAL
- Crash 与 ANR 均使用该入口，绕过 shared queue、sampling、aggregation 与 rate limit

该路径不等待网络，返回值只表示完整事件已到本地 hand-off point。若使用 `StorageType.FILE`，只能同步写非 durable ring buffer，无法获得 restart replay/acknowledged delete 语义；strict production 已要求 SQLite。

## 5. 交付语义

当前语义是 acknowledged at-least-once：

- 只有 uploader 返回完整批次成功才删除 outbox 行
- 失败保留并增加 retry count
- 本地指数退避与服务端 `Retry-After` 取较大值
- retry 失败达到 `maxRetries + 1` 或事件时间超过 7 天后清理
- 进程重启后 worker 从 SQLite 重放

不保证 exactly-once：

- `ApmEvent.eventId` 在 Line/Protobuf/codec/SQLite/IPC 全程稳定，供服务端幂等
- 服务端成功但客户端未收到响应时会重发
- SQLite 写事务原子 claim；owner-only ACK/failure；expiry 后可重领
- 网络不确定性仍要求服务端按 eventId 去重

## 6. 生命周期

```text
Apm.register before init
  -> module retained

Apm.init
  -> validate consent/runtime profile before creating SDK resources
  -> create independent diagnostics + logger
  -> create store/uploader/limiter/aggregator/sanitizer/self-monitor
  -> create business-context source; async mode starts apm-biz-context refresh
  -> create dispatcher
  -> optional ProcessEventCoordinator
  -> start managed signed-config polling
  -> start every registered module that passes process/dynamic/gray filters

Apm.register after init
  -> atomic duplicate-name check
  -> initialize and start immediately when filters allow

Apm.stop
  -> state=null, reject new emits
  -> stop signed-config polling
  -> stop business-context refresh
  -> stop self-monitor/coordinator
  -> module.onStop
  -> drain dispatcher with timeout
  -> flush aggregation residue
  -> stop worker/uploader
  -> close store

Apm.revokeCollectionConsent(application)
  -> sticky process-local revoke gate, reject new emits
  -> stop config/modules/IPC producers
  -> discard dispatcher queue; do not flush aggregation
  -> stop uploader before erasing event stores
  -> clear SQLite/File event data and IPC ready/temp files
```

模块启动受进程策略、全局 `apm.enabled`、模块签名开关、`GrayReleaseController` 和当前 AutoThrottle 集合过滤。托管 provider 发布新可信快照后在 `initLock` 下动态停止或恢复模块；自动健康降级立即生效，连续 3 个健康周期后才释放，并在恢复时重新检查其余门禁。撤回不是普通 stop：无参 API 只在活动 runtime 可定位数据，冷启动/停止态必须传 `Application`；多进程宿主必须向每个 SDK 进程传播撤回以关闭各自内存 producer。

## 7. 多进程

多进程协调默认关闭。开启时主进程为 uploader process：

```text
child process event
  -> lock-free buffer under atomic 4 MiB pending budget
  -> one fixed-delay apm-ipc-write task every 500 ms; max 16,384 events/tick
  -> split each ready file at 100 lines or byte budget
  -> reject raw event above 256 KiB / split ready files at 1 MiB
  -> write unique .tmp
  -> under cross-process lock, enforce 16 MiB ready-directory budget
  -> rename/copy to .ipc
  -> main process scan every 5 s
  -> stream bounded lines and decode complete ApmEvent
  -> dispatcher
```

critical 事件绕过缓冲并同步发布，event/file/directory 超预算会把准确的稳定 drop reason 返回调用方。上传进程把 CRITICAL 事件直接同步交给 SQLite；只有下游确认接受才删除 ready `.ipc`，拒绝、recoverable 存储异常或消费回调未就绪时保留整文件重试。整文件重试可能重复投递已接受的前序行，因此语义是以稳定 `eventId` 去重的 at-least-once。已发布 `.ipc` 不按年龄先行删除，16 MiB directory budget 负责空间边界；只有未完成 `.tmp` 在 5 分钟后清理。rename 失败会在同一预算锁内 copy 到 ready 文件后删除 temp，这一 fallback 不应被解释成跨文件系统事务保证。正常事件不会为每个 emit 创建 executor task；达到时间/条数条件的 flush 被合并。

## 8. 线程与执行器

| 线程/执行器 | 作用 | 优先级意图 |
|---|---|---|
| `apm-dispatcher` | 解析、聚合、限流、脱敏、批量落盘 | 后台管线；当前为命名 daemon Thread |
| `apm-persistent-upload` | outbox 顺序上传与重试 | background |
| `apm-aggregation` | 过期聚合窗口 flush | background |
| `apm-self-monitor` | SDK 健康报告/auto-throttle | background |
| `apm-biz-context` | 可选业务上下文异步刷新与 LKG 发布 | background；emit 不等待 provider |
| `apm-diagnostics-writer` | 独立诊断 JSONL 落盘 | background |
| `apm-ipc-write` / `scan` | IPC 合批发布/扫描 | background |
| 模块采样线程 | Memory/GC/Thread/Battery 等 | background 或 measurement |
| `apm-anr-*` | Watchdog/SIGQUIT 分析 | measurement |
| slow-method sampler | 主线程栈采样 | measurement |

`ApmExecutors` 统一 daemon、线程名和两级优先级。`apm-uploader` 无法依赖 core，因此保留模块内执行器和 `UploaderLogger`；其 `RetryingApmUploader` 通过模块内工厂为有序 worker 与 delayed-retry scheduler 显式设置稳定 `apm-` 线程名、daemon 和 `Thread.MIN_PRIORITY`，而不是把依赖方向倒置。

## 9. 资源保护

- dispatcher queue：2048 条 + 8 MiB 估算保留内存；调用线程不执行 durable 序列化
- dispatcher module isolation：默认开启；75% 高水位后单一 NORMAL/LOW 来源最多占总容量 50%，HIGH/CRITICAL 绕过
- dispatcher drain：32
- biz-context refresh：异步模式 100 ms–24 h 有界；显式刷新最多保留一个 pending 请求
- SQLite rows：50,000
- SQLite live payload：64 MiB 逻辑预算（不含 page/WAL；活动租约可使回收延后）
- SQLite durable event：256 KiB 软上限（codec 仍保留 2 MiB 硬上限）
- RateLimiter bucket LRU：256
- non-durable uploader queue：500
- aggregation bucket/sample：有硬上限
- stack fingerprint cache：有硬上限
- IPC pending：4 MiB；lock-free producer + 单一 500 ms fixed-delay writer
- IPC raw event：256 KiB
- IPC ready file：1 MiB；最多 100 行
- IPC ready directory：16 MiB；跨进程文件锁内检查
- codec event payload：2 MiB 硬上限
- V2 HTTP envelope：gzip 前默认 1 MiB、绝对 4 MiB；按实际编码拆批
- event map：4096 entries
- diagnostics memory/queue：200 / 256 records，且各自最多 4 MiB
- diagnostics files：3 × 512 KiB

发生过载时优先丢低价值事件并记录自监控，而不是让资源无界增长。

| 能力 | 默认 |

| Multi-process IPC budget | 4 MiB pending / 256 KiB event / 1 MiB file / 16 MiB directory |
| HTTP Gzip | 开（只有 HTTP endpoint 时生效） |
| Dynamic HTTP endpoint | 关；开启后仍只接受无凭据 HTTPS URL |

| Self monitoring / auto-throttle | 开 |
| Aggregation | 关 |
| PII sanitization | 开；文本规则 + 高置信敏感字段名 |

| Multi-process coordination | 关 |
| Native crash | 关 |

## 11. 监控层接入分类

自动/生命周期驱动：Crash、ANR、Memory 周期采样、Launch、FPS、Thread、GC、Render。

宿主接线：Network、SQLite、IPC 显式 trace、指定 WebView install/wrapper、注册 ThreadPoolExecutor、Battery 的 WakeLock/GPS/Alarm、IO stream wrapper、Launch 精细阶段。

编译期接线：Slow Method ASM 插件。

公共 API 无法可靠支持的通用 Binder hidden hook、进程级 WebView auto-register、通用 thread leak 和 GPU overdraw 字段已弃用并默认关闭。线程池 backlog、WebView delegate instrumentation 与 FrameMetrics 使用显式/受支持 API 实现。

## 12. 自监控与独立诊断

`SdkSelfMonitor` 记录 emit、drop、queue size、upload latency、internal errors、dispatcher 模块隔离丢弃、固定流水线阶段延迟、存储拒绝/容量淘汰、诊断队列丢弃和诊断文件失败。`dispatcherModuleIsolationDropCount` 是总 drop 的可归因子集。阶段延迟覆盖 `resolve/sampling/aggregate/rateLimit/sanitize/storeHandoff`，每项输出 count、平均微秒、P95 直方图桶上界与最大微秒；固定 6 × 22 桶不保留原始样本，关闭 self-monitor 时不执行计时。健康报告可驱动 `AutoThrottle`：高丢弃率或高上传延迟时立即停用低优先级模块；极高丢弃率再停用部分 normal 模块。阶段延迟当前只用于归因，不参与 throttle。恢复要求连续 3 个周期同时满足 drop rate <= 20% 和平均上传延迟 <= 3 秒；迟滞区间或新退化会清零恢复计数。

每个 `sdk_health` 先把仅含数值计数的摘要写入独立诊断 journal，再以 HIGH 优先级尝试普通事件管线；后者仍可能受采样、限流或极端拥塞影响，但前者不依赖 dispatcher/outbox/uploader。每个真实 loss 以总数 + `dropReason.<reason>` + `dropPriority.<priority>` 三个维度记录；SQLite capacity eviction 与 retry/age prune 返回精确 priority，兼容聚合结果缺少 priority 时进入 `unattributed`，不伪造分类。详细 SDK 错误同样写入独立的 Logcat + 内存环 + app-private 滚动 JSONL；journal 按 Android 进程隔离，聚合导出会合并所有进程。内存和写队列同时受条数/字节双预算约束，冷却期间先等待再出队，读写失败分开统计。`ApmDiagnostics` 提供同步兼容及 executor 异步读取/导出、当前进程清理和显式全进程清理；诊断包默认不自动上传。

## 13. 外部演进边界

客户端可独立完成的 strict production profile/显式 consent/撤回清理、eventId、typed wire V2、typed durable codec v3/legacy 读取、SQLite schema v4（v3→v4 为纯加性 claim 排序索引迁移）、claim lease、动态短期鉴权、签名配置/LKG/kill switch/采样/限流/endpoint、优先级感知背压、默认隐私保护、运行时快照、microbenchmark 固定预算和真机 A/B/离线/重启 smoke/24h/72h 门禁已完成。Dispatcher 满队列高优先级替换使用固定 LOW→NORMAL→HIGH FIFO 扫描，不再复制排序全队列；现行 AndroidX gate 包含历史 codec/SQLite 三项和新增的 accepted/full-queue 两项，后两项已编译但尚无真机 JSON。device-soak result schema v2 明确区分 control CPU、enabled 绝对 CPU 和带符号 delta，并从原始 samples 重算校验；当前 schema v3 绑定 exact APK、clean source、matrix/budget/runner 哈希、lane 及完整设备身份，受控设备实验室用 API 24–28 / 29–33 / 34–36 三个不重叠 lane、六个 lane/profile 工件及 OEM/device/reset 多样性做 fail-closed 汇总。schema v1/v2 仍可读取历史单工件，但不能进入当前矩阵验收。UID power 优先读取 package-scoped 值，OEM 隐藏时读取精确 current-checkin `pwi,uid`，只有累计值严格增长才构成证据，平坦/回退仍 fail closed。原绝对 CPU 门禁保持不变。2026-07-23 的物理设备结果证明当时三项 microbenchmark 预算通过；FPS 静态页面 VSync observer 修复后，两轮 smoke 在原 `20%` CPU 上限下以 `12.928%`、`12.362%` 全项通过。2026-07-24 当前 Redmi 五分钟诊断的 checkin UID power 仍为零，不构成功耗接受。2026-07-25 的 Redmi 24h 重试由用户主动取消，未生成 JSON，因此不是通过或失败证据。矩阵 plan 校验、门禁实现与短 smoke 通过仍不等于完整生产准入；五项 microbenchmark、24h/72h 和长稳功耗延期到预生产受控设备实验室，不阻塞当前客户端迭代。2026-07-31 已用真实 `HttpApmUploader` 与独立参考服务端完成 V2/Gzip/exact ACK/typed persistence/eventId replay 的 loopback 联调；生产 Collector 仍必须按 [Wire V2](../protocol/COLLECTOR_WIRE_V2.md) 在 PostgreSQL/TLS 环境部署并完成故障验收。Token 签发/撤销、配置签名与 rollout、查询/告警、24h/72h/趋势存储、Native 符号化、外部 Maven 与云端 runner 的唯一清单由独立 `AndroidAPM-Server` 仓库的 `docs/云端待建设清单.md` 维护。

## 14. 时间与异步快照语义

collector event、持久化 lease/age、文件 mtime 与 HTTP-date 使用 Unix epoch；进程内 duration、timeout、cooldown、dedup、rate-limit 和聚合窗口统一通过 `ApmClock` 使用单调时钟。`Apm.emit` 以及直接 `ApmEvent` 的 dispatcher/多进程异步 hand-off 都会冻结 fields、globalContext、extras，避免调用方后续修改污染已发生事件。
